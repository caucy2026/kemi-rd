# 暗黑1原生 Android 移植与高清超分可行性报告

文档日期：2026-08-08  
评估对象：KEMI PAD（ARM64、1920×1280、横屏、双屏能力）  
候选引擎：DevilutionX  
现有参考工程：`/Volumes/ORICO/kemi/kemi-diablo2-android`

## 1. 结论

暗黑1可以重新启动移植，而且技术风险显著低于当前暗黑2方案。

建议使用 **DevilutionX 原生 ARM64 Android 版本**，不要再把 Windows x86 暗黑1放进 Wine/Box64。
DevilutionX 已经具备完整游戏逻辑、Android 工程、SDL 渲染、触摸/手柄/鼠标键盘、宽屏、中文、
存档和音频支持。我们主要需要做 KEMI 产品化、双屏键盘、资源安装流程、PAD 操作布局和高清
输出，不必重新逆向游戏逻辑。

当前暗黑2所谓“AI超分”可以用于暗黑1，但要准确理解：当前已实现的是 **FSR1 风格的 EASU
空间边缘重建 + RCAS 自适应锐化**，不是神经网络推理。算法数学和 GLSL shader 可以复用，
Winlator/XServer 的 Java 外壳不能原样搬过去。暗黑1应把超分直接接入 DevilutionX/SDL 的最终
画面输出，因此链路更短、延迟更低、CPU和GPU余量更大。

推荐首版采用三档可切换方案：

1. `像素清晰`：整数缩放/Scale2x，保证字体、图标和像素画不糊；
2. `高清平滑`：EASU + RCAS，改善人物、地砖、斜线和光照边缘；
3. `智能混合`：世界画面走 EASU，UI/字体走整数缩放，最后合成。这是最终质量上限最高的路线。

## 3. 为什么暗黑1比当前暗黑2更适合 PAD

| 项目 | 当前暗黑2方案 | 暗黑1 DevilutionX方案 |
|---|---|---|
| CPU架构 | x86 Windows程序，经 Box64/Wine 转译 | 原生 ARM64 C/C++ |
| 图形链路 | 游戏→Wine→XServer→GLES→Android | 游戏引擎→SDL/GLES→Android |
| 输入 | Android→覆盖层→X11鼠标键盘→游戏 | Android/SDL直接进入游戏控制系统 |
| 分辨率 | 原程序固定800×600为主 | 引擎可配置分辨率、宽屏和缩放 |
| 触摸控制 | 我们自行映射传统PC输入 | 上游已有触摸、手柄、鼠标键盘支持 |
| 中文 | 依赖旧版游戏字库和补丁 | 上游已有多语言与中日韩文字改进 |
| 暂停恢复 | Wine/XServer/GL三层生命周期 | 单个原生Activity/SDL Surface |
| 性能余量 | 转译、X11合成和两次后处理 | 可把更多GPU预算留给高清处理 |
| APK体积 | 运行环境和游戏内容很大 | 引擎本体小，主要体积来自合法资源 |

这意味着暗黑1不应复制暗黑2的“容器产品”，而应做真正的原生 Android 游戏产品。

## 4. 现有暗黑2高清算法到底是什么

当前链路位于：

- `app/src/main/java/com/winlator/renderer/material/WindowMaterial.java`
- `app/src/main/java/com/winlator/renderer/effects/RCASEffect.java`
- `app/src/main/java/com/winlator/renderer/EffectComposer.java`
- `app/src/main/java/com/winlator/XServerDisplayActivity.java`
- `app/src/main/java/com/winlator/widget/XServerView.java`

数据流为：

```text
800×600 暗黑2纹理
  → EASU：12点采样、方向边缘估计、椭圆重建核
  → 1600×1200/全屏离屏FBO
  → RCAS：中心和上下左右5点、自适应锐化和过冲限制
  → Android Surface
  → 最后叠加高清PAD按钮
```

重要特征：

- 无模型文件、无训练权重、无 NPU；
- 每像素运算由 GPU fragment shader 并行执行；
- CPU只管理纹理、FBO、uniform和draw call；
- 不使用运动矢量、深度或历史帧，所以可接在任何最终2D画面之后；
- 当前暗黑2真机安全档是30 Hz合成，瓶颈主要是老Mali的纹理带宽和全屏后处理。

所以它能移植到暗黑1，但应称为“GPU空间超分/智能边缘重建”，不应对外宣传成神经网络AI，
除非以后真正加入 ncnn/TFLite/NNAPI 模型。

## 5. 暗黑1中的接入位置

### 5.1 推荐接在 SDL 最终输出层

DevilutionX 原生渲染完成游戏场景和UI后，会交给 SDL 纹理/renderer呈现。首版最稳的接法是：

```text
DevilutionX 软件/SDL 游戏画面
  → 原始场景纹理
  → OpenGL ES FBO
  → EASU 或 Scale2x
  → RCAS（可关闭）
  → 1920×1280 Surface中的目标游戏区域
  → Android/KEMI原生辅助层（若需要）
```

优点：

- 不修改怪物、寻路、战斗、存档等游戏逻辑；
- 不需要运动矢量；
- shader失败时可退回上游已有的 nearest/bilinear/anisotropic；
- Android、桌面版可以共享算法，但只在KEMI产品配置中默认开启。

### 5.2 最终版应拆分世界层和UI层

暗黑1是像素美术。对所有内容统一做EASU会出现矛盾：世界场景更平滑，但小字和背包格可能
变软；统一RCAS又可能让字体产生白边。

源码可控以后，应把合成拆成：

```text
世界/角色/怪物/光照 → EASU + 轻RCAS
字体/背包/血球/按钮 → 整数缩放或高质量最近邻
Android触控图标       → 原生分辨率
最终Alpha合成          → 1920×1280
```

这比暗黑2“只能拿到最终窗口纹理”更有优势，也是重做暗黑1真正值得投入的地方。

## 6. 分辨率策略

暗黑1经典画面基础是640×480，但 DevilutionX 支持可配置分辨率、Fit to Screen、Upscale、整数缩放
以及多种Scaling Quality。不能简单把640×480强行拉满1920×1280。

### 6.1 1920×1280 PAD推荐候选

方案A：经典4:3

- 内部逻辑视口：800×600或960×720；
- 输出游戏区：1600×1200；
- 上下各40像素、左右留操作安全区；
- 适合保留原版构图和较大的UI。

方案B：宽屏原生视野

- 内部视口：960×600或1024×640；
- 输出：1920×1200；
- 上下各40像素；
- 世界可显示更多内容，但必须检查UI大小和游戏平衡感。

方案C：640×480严格复古

- 2×整数缩放到1280×960，四周留黑边/操作区；
- 最清晰、最低成本，但画面占屏较小；
- 可作为“像素原版”模式，而不是默认模式。

首版建议使用方案A作为默认，方案C用于A/B。不要一开始追求640×480→1920×1280的非整数满屏，
那会同时破坏比例和像素字。

## 7. EASU+RCAS在暗黑1上的预期效果

### 7.1 会明显改善的内容

- 角色和怪物精灵的斜边、武器轮廓；
- 地牢墙角、地砖对角线、楼梯；
- 动态光照圆边和阴影过渡；
- 放大后的火焰、法术和传送门轮廓；
- 非整数缩放时的整体稳定性。

### 7.2 不会凭空改善的内容

- 原资源中不存在的脸部、盔甲和地面纹理细节；
- 原始精灵动画帧数；
- 低分辨率字体字模本身的笔画设计；
- 压缩或调色板造成的颜色阶梯。

### 7.3 可能变差的内容

- 8/12像素级小字体可能被EASU软化；
- 背包格、生命球边框和单像素线可能被RCAS加出光环；
- 调色板动画、水和火可能因过强锐化出现闪烁；
- 对像素画使用过度平滑会失去原版美术风格。

因此暗黑1不能只保留一种“最大锐化”配置。必须有像素模式、平滑模式和回退机制。

## 8. 参数起点

建议第一轮A/B从以下参数开始：

| 配置 | 输入 | 输出 | EASU | RCAS stops | 用途 |
|---|---:|---:|---|---:|---|
| P0 原版 | 640×480 | 1280×960 | 关 | 关 | 像素基线 |
| P1 像素清晰 | 800×600 | 1600×1200 | Scale2x | 关 | 字体/UI对照 |
| P2 高清均衡 | 800×600 | 1600×1200 | 开 | 1.0 | 推荐起点 |
| P3 高清锐利 | 800×600 | 1600×1200 | 开 | 0.75 | 世界细节对照 |

暗黑2当前0.75 stops不应无条件复制。暗黑1像素对比度更强，建议先从1.0（较弱锐化）开始。

## 9. 真正神经网络AI超分是否值得做

技术上可以，但不应作为暗黑1首版依赖。

可行架构：

```text
低分辨率世界层
  → Vulkan/ncnn FP16或INT8
  → FSRCNN/ESPCN/轻量残差网络 2×
  → 可选轻RCAS
  → UI整数缩放合成
```

模型必须用合法取得的暗黑1画面构造训练集，并分别处理场景、精灵、光照和文字。通用动漫/照片
模型很容易生成不存在的砖纹、脸部和字体笔画，连续帧还会闪烁。

真正AI路线的准入条件：

- 1920×1200下端到端合成稳定≥30 FPS；
- P95帧时间≤33.3 ms，不能只看平均值；
- 连续移动时不出现纹理呼吸和闪烁；
- 文字、地图和背包不进入神经网络；
- 模型加载失败自动切回EASU；
- 温升和功耗进行至少30分钟持续测试。

在这些条件满足前，FSR1空间重建是风险更低的量产默认方案。

## 10. PAD操作方案

DevilutionX已经理解暗黑1的游戏语义，操作层应调用引擎动作，而不是模拟一堆PC快捷键。

建议：

- 左摇杆：角色八方向移动，不与鼠标光标绑定；
- 主攻击/互动：引擎根据目标判断攻击、开门、拾取、交谈；
- 原地攻击：显式调用站立攻击动作；
- 技能：打开原生技能列表，触摸选中后绑定右侧主技能；
- 显示物品：按住显示、松开恢复，另提供“常显”选项；
- 地图：触摸开关，支持缩放与透明度；
- 鼠标模式：外接鼠标直接走SDL鼠标事件，可点击世界和原生UI；
- 键盘：单屏弹本屏，双屏按KEMI文档投到另一屏；
- 摇杆活动时只隐藏鼠标视觉，不破坏鼠标位置和点击能力。

因为源码可控，可以直接查询当前可交互目标、技能和地面物品，避免暗黑2覆盖层“按钮看起来能按，
但只是在模拟未知快捷键”的问题。

## 12. 开发路径

### 阶段0：许可闸门

1. 确认用途是内部非商业测试还是未来商业发布；
2. 保存DevilutionX确切版本、commit和许可证；
3. 商业用途先联系上游获取书面许可或选择法律允许的替代底座；
4. 明确DIABDAT.MPQ只由合法来源导入。

验收：许可清单、第三方声明、资源边界形成文档。

### 阶段1：上游原版基线

1. 在外置盘新建独立工程，不复用旧暗黑1项目；
2. 固定DevilutionX稳定tag和commit；
3. 使用官方`android-project`构建arm64-v8a APK；
4. 在62测试启动、导入共享版/合法完整资源、创建角色、进城、下地牢；
5. 测鼠标、触摸、键盘、手柄、音频、暂停恢复和存档。

验收：连续玩30分钟，无崩溃；声音正常；存档重启可恢复；原生输入全部可用。

### 阶段2：KEMI产品壳

1. 应用名和图标；
2. 横屏锁定、1920×1280与高度<1200自适应；
3. 首次运行资源检查与导入；
4. 单/双屏软键盘路由；
5. 中文默认和PAD默认配置；
6. 不改变上游游戏规则。

验收：新安装从零开始能完成资源导入和首次进游戏，错误信息中文且可恢复。

### 阶段3：高清基线A/B

1. 固定同一存档、场景、相机位置和截图；
2. 实现NEAREST、Scale2x、EASU、EASU+RCAS四档；
3. 先对完整最终帧处理，不立即拆层；
4. shader/FBO失败自动回退；
5. 采集平均、P95、P99帧时间及温度。

验收：所有模式可热切换；无黑屏；推荐模式稳定≥30 FPS；字体和地图不比上游默认更差。

### 阶段4：世界/UI分层

1. 找到DevilutionX世界画布和UI绘制边界；
2. 世界层输出到低分辨率FBO；
3. UI层保留逻辑分辨率或单独整数放大；
4. EASU只处理世界层；
5. RCAS裁剪到游戏区域，不处理黑边与Android按钮。

验收：人物和地牢边缘平滑；中文、背包、地图和血球保持像素清晰；GPU成本低于全屏双pass。

### 阶段5：PAD语义操作

1. 复用DevilutionX现有触摸/手柄动作；
2. 按暗黑1交互逻辑重新排布，不照搬暗黑2HUD；
3. 验证移动、攻击、原地攻击、法术、开门、拾取、背包、地图、对话；
4. 外接鼠标与触摸同时存在；
5. 每个按钮用真实游戏场景验收。

验收：从村庄进入教堂，杀怪、拾金、装备物品、施法、回城、保存退出全部独立完成。

### 阶段6：可选神经网络原型

只有阶段1到5稳定后再进行。模型作为实验模式，不能阻塞首版交付。

## 13. 性能预算

原生ARM64移除Box64/Wine/XServer后，CPU预算会明显优于暗黑2，但GPU超分成本仍与输出像素数有关。

目标预算建议：

- 游戏逻辑与SDL上传：≤8 ms；
- EASU：≤8 ms；
- RCAS：≤4 ms；
- UI合成与Surface提交：≤5 ms；
- 总P95：≤33.3 ms；
- 连续30分钟无音频爆音、无明显降频、无Surface透明恢复问题。

应优先优化：

1. RCAS只跑游戏矩形；
2. 复用FBO，避免每帧分配；
3. UI不进EASU/RCAS；
4. 合并重复requestRender；
5. 只在源画面变化时做昂贵pass；
6. 老Mali使用`highp/mediump`分级和显式采样，避免依赖不稳定的`textureGather`。

## 15. 可借鉴项目的优先级

### 第一优先级：DevilutionX

用途：完整暗黑1/地狱火引擎、Android、输入、中文、宽屏、存档。它是主底座，不只是参考。

### 第二优先级：AMD FidelityFX FSR1

用途：EASU/RCAS算法校对、常量、锐化与许可。当前工程已有GLES适配经验。

### 第三优先级：Libretro shader生态

用途：xBR、SABR、ScaleFX等像素画算法。暗黑1的字体、UI和精灵可能比通用EASU更适合这些算法。

### 第四优先级：NVIDIA Image Scaling

用途：单pass或较低成本的空间放大对照。必须单独模式A/B，不能凭理论替换EASU。

### 第五优先级：ncnn/Vulkan

用途：将来实现FSRCNN/ESPCN等轻量真正AI 2×模型。首版不建议引入。

### 仅借鉴、不做主底座

- 原始Devilution：历史参考价值高，但现代Android产品能力不如DevilutionX；
- Freeablo等不完整重实现：不适合作为可交付完整游戏底座；
- Winlator暗黑1：可以快速跑，但失去原生源码在性能、输入和分层渲染上的优势；
- PS1模拟器方案：合法性和画质不占优，操作层也更难做到游戏语义级适配。

## 17. 最终建议

建议把暗黑1捡起来，但按以下原则重启：

1. 新建独立的 DevilutionX ARM64 Android 工程；
2. 先拿上游原生Android版在62跑通完整游戏闭环；
3. 先解决许可，再决定能否成为商业预装产品；
4. 把现有EASU+RCAS移到SDL/GLES最终输出，不搬Winlator容器；
5. 默认做800×600→1600×1200的4:3高清模式；
6. 同时保留Scale2x像素模式；
7. 最终拆分世界和UI，世界平滑、文字与图标点对点清晰；
8. 操控直接调用DevilutionX游戏动作，避免再模拟一套不可靠的PC按键；
9. 真正神经网络AI放到第二阶段研究，不阻塞可玩的首版；
10. 以“进教堂、杀怪、拾金、施法、回城、存档恢复”为交付闭环。

在非商业研发前提下，技术结论是 **可行且值得做**；如果目标是商业预装，当前第一任务不是写
shader，而是解决 DevilutionX 源码许可和 Diablo 资源授权。
