# KEMI OFFICE 单屏兼容与双屏连续画布架构设计

更新日期：2026-08-09

目标设备：`192.168.3.62`
目标模式：同一 APK 自动兼容单屏设备；在目标双屏设备上把两个 `1920×1280@60Hz`
物理屏拼接为固定 `1920×2560` 逻辑画布

当前 v1.0.16 的实际画面组合、D2/D0 视口、触摸回送、加载层和跨屏键盘实现见
[双屏画面合成与联动操作实现细节](DUAL_DISPLAY_COMPOSITION_AND_LINKED_INTERACTION.md)。

## 1. 产品定义

KEMI OFFICE 只发布一个 APK。应用不得假设设备一定有两个屏幕：普通手机、平板、只有内置
屏的 KEMI 设备以及外接屏不可用的情况，都必须保持现有单屏 Office 能力。双屏连续画布是
满足拓扑门禁后的增强模式，不是应用启动的必要条件。

双屏模式不是镜像、扩展桌面或同时打开两份文档。它是一个 Office 会话在两个物理屏上的
连续显示：上屏显示逻辑画布 `Y=0..1279`，下屏显示 `Y=1280..2559`。页面允许跨越物理
接缝，滚动、缩放、选区、光标、页码和编辑状态只有一套。

双屏模式强制禁止旋转：

- 两个显示端点固定按 `1920×1280` 横向布局创建；不响应重力传感器和系统自动旋转。
- 逻辑画布固定为 `1920×2560`，运行期间不得互换宽高。
- Display 0/2 的系统 rotation 只参与一次设备坐标到逻辑坐标的变换，不能触发 Activity
  重建、文档重排或画布旋转。
- 副屏当前报告 `rotation=2`，但 Android Presentation 已将画面和输入归一化为逻辑横屏坐标；
  应用不得再次手工反转。真机标定必须确认系统是否已经应用变换，避免双重旋转。

单屏模式遵循产品配置：目标 KEMI 固定屏设备保持固定横屏；通用 Android 单屏设备可继续
使用原有单屏方向策略。禁止为了实现双屏而全局锁死所有单屏手机和平板的方向能力。

## 2. 真机事实与约束

2026-08-09 ADB 读取结果：

| 项目 | Display 0 | Display 2 |
| --- | --- | --- |
| 类型 | 内置屏幕 | HDMI/Presentation |
| 物理分辨率 | 1920×1280 | 1920×1280 |
| 刷新率 | 60Hz | 60Hz |
| 设备密度 | 320dpi | 原生 213dpi，系统覆盖 320dpi |
| 当前 rotation | 0 | 2（180°） |
| 触摸 | INTERNAL | EXTERNAL |

Android 把两块屏作为独立 Display 和独立 layer stack 管理。普通 Activity/Window 不能横跨
两个 Display；单个 WebView 也不能同时挂到两个窗口。现有 `LOActivity` 为 `singleTask`，
复制启动第二个编辑 Activity 会造成生命周期、URI 权限、保存和 Core 所有权冲突，因此禁止
采用“双 Activity + 双 Core”方案。

## 3. 总体架构

```text
DocumentSession（唯一）
  ├─ Office Core / 文档模型（唯一）
  ├─ DualCanvasController（1920×2560 逻辑坐标）
  │    ├─ viewportTop    = [0, 0, 1920, 1280]
  │    └─ viewportBottom = [0, 1280, 1920, 2560]
  ├─ SharedTileCompositor（共享清晰瓦片与页面缓存）
  │    ├─ DisplayEndpoint 0
  │    └─ DisplayEndpoint 2
  └─ UnifiedInputRouter
       ├─ Display 2 触摸 → 逻辑上半区坐标（原值回送）
       ├─ Display 0 触摸 → 逻辑下半区坐标（View 变换得到 Y+1280）
       └─ 跨屏 IME → 同一编辑焦点
```

### 3.1 运行模式

新增 `OfficeDisplayMode`，整个进程在任意时刻只能处于一种稳定模式：

| 模式 | 条件 | 逻辑 viewport |
| --- | --- | --- |
| `SINGLE` | 只有一个可用交互显示，或第二屏不满足门禁 | 当前 Activity 可用区域 |
| `DUAL_PREPARING` | 第二屏已发现，正在标定和准备同帧内容 | 仍按单屏显示 |
| `DUAL_CONTINUOUS` | 两个端点、坐标和同 generation 帧均准备完成 | 固定 1920×2560 |
| `SINGLE_FALLBACK` | 双屏端点移除、超时或异常 | 保持状态并原子回单屏 |

模式切换由 `OfficeDisplayCoordinator` 串行执行，禁止 Activity、查看器或 JavaScript 各自判断
屏幕数量。每次切换携带递增的 `displayGeneration`，过期异步回调不得重新创建旧端点。

双屏启用门禁同时满足：

1. 至少两个处于 `STATE_ON` 的可信显示。
2. 存在主显示和一个允许显示 Presentation 的外部显示。
3. 目标硬件配置允许连续画布；默认通用 Android 外接投影不自动进入连续模式。
4. 两个端点均能建立稳定的物理到逻辑坐标变换。
5. 当前文档查看器声明支持双屏；尚未适配的格式继续单屏显示，不崩溃。

门禁失败一律进入 `SINGLE`，不能弹错误阻止用户打开文档。

### 3.2 单一文档会话

`LOActivity` 继续拥有唯一 WebSocket/MobileSocket、Core、文档 URI、保存状态和关闭流程。
增加 `DualDisplayDocumentSession`，集中管理滚动位置、缩放比例、选择、光标、当前页、编辑
模式及两个端点的生命周期。任何端点都不得直接修改另一套文档状态。

### 3.3 显示端点抽象

新增统一 `DisplayEndpoint` 接口。单屏模式创建一个 `ActivityDisplayEndpoint`；双屏模式保留
主端点并增加 `PresentationDisplayEndpoint`。文档控制器只面向 endpoint 列表，不在业务
逻辑中写死 Display 0/2。

单屏端点使用真实窗口可用尺寸，不能强行渲染成 1920×1280；手机状态栏、导航栏、挖孔、
平板分屏窗口和不同 density 均从 `WindowMetrics`/Insets 计算。双屏目标设备才使用经过真机
标定的固定物理几何。

### 3.4 两个显示端点

Display 0 使用主 Activity 窗口；Display 2 使用由主 Activity 管理的 Android
`Presentation` 窗口。`Presentation` 只是第二个渲染/输入端点，不创建第二个 Core、第二个
WebView 或第二个文档实例。副屏增加/移除通过 `DisplayManager.DisplayListener` 驱动。

### 3.5 共享瓦片合成器

不能使用持续 `PixelCopy`、屏幕录制或低清截图镜像。Office Core 按统一逻辑可视区域请求
清晰瓦片，`SharedTileCompositor` 持有一份 GPU 纹理/位图缓存，并把同一帧按两个 viewport
裁剪提交到两个 Surface。跨屏页面只解码一次，两个端点引用同一缓存对象。

调度优先级：

1. 两屏当前可视区域。
2. 跨接缝瓦片和文字/光标覆盖层。
3. 滚动方向前方一屏预取。
4. 后方一屏缓存。
5. 其余缩略图和后台页面。

每个逻辑帧生成单调递增 `frameGeneration`。两个端点只有在同一 generation 准备完成后才
共同提交；超时只能继续显示上一张完整清晰帧，不允许一屏更新、一屏停留或显示黑条。

单屏模式沿用同一合成器，但只有一个 viewport 和一个提交栅栏，避免为了兼容双屏增加一次
额外复制。双屏相关线程、Presentation、第二套 Surface 和预取窗口在 `SINGLE` 时不得创建，
确保普通单屏设备的启动时间、内存和帧率不退化。

### 3.6 0108 过渡实现：PPT 高清查看与热 Core 双轨

真机证明 `WebView.draw(Canvas)` 无法把 Chromium GPU Surface 等质量复制到 D2。共享瓦片
合成器完成前，双屏 PPT 默认使用 1920px 原生页面流承载只读连续查看；Core 同时在后台
完成完整导入。Core ready 不自动撤下高清层，只有用户显式进入编辑/播放/菜单才切换。

此过渡层允许使用约 150MB GPU 纹理缓存，符合设备为文档体验预留的 2GB 资源预算。它不是
最终编辑架构：不能据此删除共享 compositor，也不能把部分 OOXML 预览当作权威编辑结果。

## 4. 模式发现、切换与状态保持

### 4.1 冷启动

应用先按单屏路径立即打开文档，不等待 HDMI 枚举。`OfficeDisplayCoordinator` 在后台读取
显示拓扑；若双屏门禁通过，进入 `DUAL_PREPARING`，准备副端点及两屏首个同 generation
清晰帧，然后一次性切到 `DUAL_CONTINUOUS`。禁止先白屏或阻塞单屏首帧等待副屏。

### 4.2 单屏切双屏

以当前单屏 viewport 中心对应的文档锚点作为双屏逻辑中心，扩展上下可视区域，不重新打开
文件、不重置缩放、不跳回第一页。两屏准备期间用户仍可在主屏操作；提交时使用最新锚点，
丢弃准备期间产生的旧 generation。

### 4.3 双屏切单屏

拔掉 HDMI、Display 关闭或副端点连续超时后，选取当前活动焦点所在页/单元格/幻灯片作为
单屏锚点；如果没有活动焦点，使用双屏逻辑中心。先让主端点显示完整单屏帧，再销毁副端点，
不能闪黑、重新解码整份文档或丢失未保存修改。

### 4.4 进程恢复

保存文档 URI、格式、滚动锚点、缩放、选区、当前页和编辑状态，不持久化旧 displayId。
进程重建后重新发现拓扑：没有副屏直接恢复单屏；副屏合格再走正常的双屏准备流程。

## 5. 固定方向与坐标映射

新增 `DualDisplayGeometry`，唯一保存物理/逻辑变换：

```text
逻辑画布：1920×2560
上端点 viewport：Rect(0, 0, 1920, 1280)
下端点 viewport：Rect(0, 1280, 1920, 2560)
```

Activity、Presentation 和专用查看器进入双屏模式时均请求固定横屏并忽略传感器方向变化。
Manifest 使用固定方向；运行时再次校验 `Configuration`，发现宽高互换时保持文档状态并重建
显示端点，不允许 Core 重载文档。

当前 `.62` 产品标定为 D2 第一屏、D0 第二屏。D2 Presentation 直接显示逻辑上半区，
因此 D2 触摸保持原坐标回送同一个权威根 View；D0 根 View 使用 `translationY=-1280`，
Android 的 View 反向坐标变换自然把 D0 触摸映射到逻辑下半区：

```text
D2: logicalX = presentationX
    logicalY = presentationY

D0: logicalX = activityX
    logicalY = activityY + 1280  // 由 View translation 反变换完成
```

D2 的 180° 物理安装方向已经由 Android Presentation 归一化，应用不能再次反转。当前代码
优先选择经过产品标定的 `displayId=2`，但仍以 `STATE_ON`、Presentation 类别和
`1920×1280` 分辨率作为门禁；新硬件的实体角色必须重新标定，不能只按 displayId 大小猜测。

## 6. 输入、滚动和键盘

- 两屏触摸进入同一个 `UnifiedInputRouter`，使用同一 gesture sequence 和 velocity tracker。
- 手指从一个屏划到另一个屏不要求 Android 提供跨屏连续 pointer；以最后速度和时间戳接续
  滚动物理模型，避免接缝处速度归零。
- 缩放锚点使用逻辑坐标，缩放后两屏同步重排和刷新。
- 点击、长按、选区拖柄、批注和超链接全部映射到统一文档坐标。
- 键盘继续遵守 `cross-display-keyboard.md`：任何 KOffice 输入请求都通过跨屏代理。双屏连续
  模式下，键盘覆盖的屏幕临时缩小对应 viewport，但文档逻辑画布和另一屏不重排；键盘关闭
  后恢复。
- 单屏设备不存在可用对侧屏时，键盘必须回到当前 Activity 的标准 Android IME 路径；不能
  为等待不存在的跨屏代理而丢失输入焦点。

## 7. 各格式适配

| 格式 | 双屏行为 |
| --- | --- |
| Word | 连续页面流贯穿两屏；页间距和页码按统一 Y 坐标计算 |
| PPT | 连续瀑布流；左侧缩略栏可只放上屏，主内容跨两屏；缩略图选中同步 |
| Excel | 两屏共享行列冻结、滚动偏移和选区；下屏 Y 坐标增加 1280 |
| PDF | 连续页面统一布局；跨接缝页面不得二次解码 |
| 文本/CSV/JSON/XML 等 | 共享索引和 adapter 数据，以统一滚动位置驱动两个只读端点 |
| HTML/EPUB/SVG | 禁止复制两个独立 WebView 状态；先进入共享渲染快照/分页端点，再开放编辑 |

每种格式都必须声明 `supportsDualContinuous()`。返回 false 只表示暂时用单屏，不得影响打开、
查看、编辑、保存和退出。完成一种格式的双屏适配后，必须同时跑该格式的单屏回归。

### 7.1 统一加载反馈规则

- Activity 创建时预分配一套 `DualDisplayLoadingOverlay`，生命周期内复用，不在文档解码
  热路径动态 inflate、解析 drawable 或建立动画对象。
- Word/PPT/Excel 等确定性 Core 慢导入在 Activity 首帧立即显示常驻加载层；重复 Core
  progress start 只原位更新，不能重置动画。PDF、文本等可能在 1 秒内完成的专用查看器
  才使用 1000ms 延迟门限，及时完成则取消回调，禁止短文档闪一下加载卡片。
- 超过 1000ms 时，上屏卡片位于连续画布高度的 1/4，下屏卡片位于 3/4；不得依赖
  `match_parent` 推断双屏高度，双屏必须明确继承根画布 2560px。
- “首个可用画面”包括 Core 清晰首帧、PPT 原生清晰预览、PDF 第一页、表格首个可操作
  viewport、文本/结构化/Web 查看器首个已提交 viewport。后台预取或 Core 后续解码不得
  重新启动已经完成的打开动画。
- 单屏只显示一张居中卡片；主页、设置等非文档页面不得启动文档加载计时。
- 失败、退出、Activity 销毁和 generation 切换必须取消待执行回调并释放父 View 引用，
  禁止错误文件留下永久遮罩。

## 8. 生命周期与容错

- 第二屏插入：保持当前单屏内容，创建副端点；准备好同 generation 清晰帧后原子进入双屏。
- 第二屏移除：立即销毁 Presentation，保留主端点、文档 URI、滚动中心、编辑和未保存状态，
  降级为单屏。
- 副端点渲染异常：熔断副端点，主屏继续工作并提示“双屏显示已降级”，不能关闭文档。
- Core 异常：沿用现有修复缓存和重启策略；两个端点共同保持最后清晰帧。
- 退出：只执行一次保存/关闭；两个显示窗口共同退出并返回打开文档的原目录。
- 普通单屏设备永远不能因为 Display 2 不存在产生异常、重试循环、等待动画或功能缺失。

## 9. 性能预算

- 两屏联合目标：稳定 ≥30fps；最低验收 ≥20fps；P95 帧时间 ≤33ms。
- 两屏画面 generation 差为 0；提交时间差目标 ≤8ms，硬门禁 ≤16ms。
- 不降低文字和图片清晰度，不用模糊帧换取帧率。
- 允许使用最多 2GiB：可视瓦片、前后各一屏预取、页面位图和 GPU 纹理必须分级限额。
- Core 解码一次；同一逻辑瓦片不得因两个 Display 重复请求和重复解码。
- 主线程只处理输入与帧提交，解码、布局、缓存淘汰和纹理上传使用有界工作线程。
- 单屏性能零退化门禁：同一 APK 相对 v1.0.3，冷开 P95 不增加超过 5%，稳态滚动 P95
  不增加超过 1ms，内存不增加超过 64MiB；未启用双屏时不得常驻副端点资源。
- 内存预算按模式切换：单屏沿用现有限额；只有 `DUAL_CONTINUOUS` 才允许提升到 2GiB。

## 10. 实施阶段

### 阶段 A：模式协调器、单屏基线与空白双端点

先记录 v1.0.3 单屏打开、滚动、内存和退出基线；实现 `OfficeDisplayMode`、拓扑门禁、固定
方向、Display 发现、TOP/BOTTOM 标定、Presentation 生命周期、统一坐标变换和双屏测试图。
此阶段不接 Office Core，先证明单屏无退化、两个 Surface 同帧、触摸坐标正确。

### 阶段 B：只读共享画布

先接 PDF 和 Word 只读连续页面，验证共享缓存、跨接缝页面和同步滚动；禁止使用屏幕镜像。

### 阶段 C：Office 三格式

依次接 Word、PPT、Excel 的 tile/overlay/选择状态，建立双屏可视区联合调度和原子提交。

### 阶段 D：编辑、跨屏键盘与容错

接入光标、选区、保存、跨屏 IME、屏幕热插拔、Core 恢复及返回原目录。

### 阶段 E：全部查看器与 Release

适配 PDF 和所有专用查看器，完成大小文档压力测试、版本自动递增、Release 构建及在线更新。

## 11. 验收门禁

1. 只有一个 Display 的手机、平板和目标设备均能正常打开、操作、保存、退出所有支持格式。
2. 单屏不存在等待副屏、空白副窗口、跨屏键盘死等或 FATAL/ANR，性能满足零退化门禁。
3. 双屏设备两块物理屏均为 1920×1280；旋转设备或切换系统自动旋转时布局不旋转、不重载。
4. 标定页证明上屏逻辑 Y=0、下屏逻辑 Y=1280，Display 2 的 180° 画面和触摸均正确。
5. 一页内容跨接缝时文字、线条和图片连续，接缝两侧位置误差 ≤1px。
6. 在任一屏滑动，两个屏幕同步；帧 generation 差为 0，提交差 ≤16ms。
7. Word/PPT/Excel/PDF 大小文档连续滚动 ≥20fps、无模糊、黑条、白页、ANR/FATAL。
8. 任一屏点击、缩放、选择和翻页作用于同一文档状态。
9. 编辑、跨屏键盘、保存、退出、重开和返回原目录通过。
10. 运行中拔掉/恢复 HDMI 不崩溃、不丢编辑状态，并能单屏降级/原子恢复双屏。
11. 双屏内存峰值在 2GiB 预算内，同一瓦片没有双份解码；单屏不创建副端点资源。
12. 每轮同时保留单屏与双屏截图/录像、frame timeline、内存、关键日志和结论；任一项失败
    即不发布。

## 12. 明确禁止的实现

- 禁止双 Core、双文档实例或两个 Activity 各自打开同一 URI。
- 禁止把主屏持续截屏后传给副屏。
- 禁止通过降低分辨率、滚动时模糊或停手后再清晰来伪造流畅。
- 禁止两个屏独立滚动、独立缩放或独立保存。
- 禁止硬编码 Display 2 永远是物理下屏而不做标定。
- 禁止方向传感器或系统旋转触发双屏画布宽高交换。
- 禁止在普通单屏设备上强制创建虚拟第二屏、固定成 1920×1280 或改变原有窗口布局。
- 禁止为了双屏适配破坏单屏打开速度、滚动、编辑、保存和跨屏键盘降级路径。
