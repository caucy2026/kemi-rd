# 设备无关仿真研发与验收通用手册

版本：1.0
适用范围：移动端、嵌入式、桌面端、服务端及其他依赖真实硬件/云端构建的项目

## 1. 文档目的

设备无关仿真用于在昂贵的编译、烧录、部署和真机测试之前，低成本、可重复地证明某个设计在
逻辑上成立，并尽早淘汰确定会失败的架构。

它解决的是以下问题：

- 调度是否让可见工作优先，而不是被后台任务饿死；
- 旧请求、旧会话和旧视口是否能被取消或拒绝；
- 缓存窗口、内存上限和淘汰规则是否满足约束；
- 渐进加载是否真的减少首屏前工作量；
- 状态机在打开、操作、关闭、超时、重开时是否保持一致；
- 容错分类是否把损坏、受保护、复杂和正常输入送入正确路径；
- 新架构相对旧架构是否有可量化收益。

仿真不是“伪造真机结果”。它不能证明真实解码器能正确打开文档，不能证明 GPU/WebView/驱动
没有缺陷，也不能直接证明 FPS、功耗、温升、触控手感或视觉正确性。最终完成定义仍然是：

> 仿真证明设计值得构建；编译证明代码可以交付；真机证明用户可以完成任务。

## 2. 什么时候应该仿真

以下情况应先仿真，再申请真机或启动耗时构建：

1. 一次完整构建、部署或测试成本较高；
2. 问题包含队列、并发、缓存、状态机、重试、超时或资源预算；
3. 同一个现象已有多轮真机试参，但缺少稳定改善；
4. 需要比较两种以上架构，而不是验证一个简单代码分支；
5. 失败输入容易导致崩溃、OOM、死锁或数据损坏；
6. 真实设备数量少、设备被多人共享，或测试窗口有限；
7. 需要在 CI 中阻止已知坏架构进入昂贵的下游 job；
8. 需求包含明确量化约束，如 P95 延迟、内存上限、取消率、缓存命中率或首屏工作量。

以下情况通常不应把仿真作为主要手段：

- 改一个确定性的文案、颜色或布局间距；
- 需要判断图片是否发黑、文字是否模糊、动画是否自然；
- 问题只在特定 GPU、驱动、系统服务、输入法或多屏系统上出现；
- 需要验证真实第三方解码器、系统 API、文件权限或硬件接口；
- 需要给出真实 FPS、功耗、温度、首屏时间或竞品对比结论。

这类问题应直接做静态检查、单元测试、集成测试或真机测试。不要为了“有仿真”而仿真。

## 3. 仿真层级与选择

| 层级 | 输入 | 主要验证 | 运行位置 | 能否替代真机 |
|---|---|---|---|---|
| 纯算法仿真 | 合成事件、参数、状态 | 调度、复杂度、缓存、状态机 | 本机/CI | 不能 |
| 夹具驱动仿真 | 脱敏真实文件的结构/元数据 | 分类、边界、渐进解析策略 | 本机/CI | 不能 |
| 组件集成仿真 | 真实模块 + fake I/O/时钟 | 协议、生命周期、错误传播 | 本机/CI | 不能 |
| 模拟器/虚拟设备 | 应用与虚拟 OS | Activity、权限、基础交互 | 本机/CI | 部分 |
| Hardware-in-the-loop | 真硬件 + 自动脚本 | 驱动、性能、视觉、交互 | 实验室/产线 | 属于真机验收 |

选择最小且足够的层级。能用 200 行确定性模型验证的调度规则，不应先启动 20 分钟构建；必须
由真实 GPU 才能判断的问题，也不应继续在纯 Python 模型中堆参数。

## 4. 在哪里仿真

### 4.1 本机

本机负责快速迭代和失败定位，要求：

- 无网络也能运行核心断言；
- 依赖尽量只使用语言标准库；
- 一次运行最好小于 10 秒，最长不超过常规单元测试预算；
- 支持人类可读输出和机器可读 JSON；
- 固定随机种子、虚拟时钟、输入顺序和数据规模；
- 失败时输出是哪条不变量、实际值与期望值。

### 4.2 CI

CI 负责形成不可绕过的合并/构建门禁：

```text
checkout
   ↓
仿真与负面对照（秒级）
   ↓ PASS
源码/补丁静态绑定检查
   ↓ PASS
编译、链接、打包（分钟级）
   ↓ PASS
制品完整性检查
   ↓ PASS
真机/实验室验收
```

仿真 job 应位于昂贵构建之前。失败时不启动后续构建；成功时上传 JSON 结果、版本、输入摘要和
哈希，便于复现。不要让仿真 job 安装整个产品构建链，否则会失去“快速淘汰”的价值。

### 4.3 仿真代码放在哪里

推荐结构：

```text
scripts/
  simulate-<subsystem>.py
tests/
  fixtures/
docs/
  engineering/
  performance/
.github/workflows/
```

- 可执行模型放 `scripts/` 或测试目录；
- 小型、可公开、脱敏的输入放 `tests/fixtures/`；
- 方法、假设、边界和历次结果放 `docs/`；
- CI 只调用仓库内版本化脚本，不把关键逻辑写成 workflow 中的大段内联代码。

## 5. 从第一性原理建立仿真

### 5.1 先定义用户结果

从用户能感知的结果开始，不从现有类名或某个待调参数开始。例如：

- 当前视口必须优先于不可见预取；
- 快速滑动后，旧视口结果不得覆盖新视口；
- 关闭文档后，下一份文档必须能复用热引擎且不接收上一会话消息；
- 大表首屏前最多解析 256 行，完整索引可以后台继续；
- 受保护文件必须给出可解释失败，不崩溃、不伪造内容。

### 5.2 把系统拆成最小状态与事件

只保留影响决策的变量：

- 状态：`COLD / HOT_IDLE / ACTIVE / CLOSING / FAILED`；
- 事件：打开、视口变化、滚动开始、滚动停止、结果返回、关闭、超时；
- 资源：工作线程数、队列长度、缓存字节、在途请求数；
- 身份：session epoch、generation、document ID、request ID；
- 输出：可见完成时间、取消数、错误分类、峰值内存、最终状态。

不要在模型里复制整个生产框架。模型越大，越可能复刻实现错误而不是验证设计。

### 5.3 写出不变量

每条不变量必须能转为布尔断言，例如：

```text
所有活动文档 ID > 0
连续打开的文档 ID 不重复
旧 epoch 的响应接受数 = 0
手势期间后台预取启动数 = 0
缓存占用 ≤ 预算
损坏输入分类 = invalid，而不是 crash
```

“应该更快”“应该流畅”不是可执行不变量。必须转换成数字或明确状态。

### 5.4 同时实现基线与候选

仿真至少包含：

- baseline：当前或旧架构；
- candidate：待交付架构；
- 相同输入和时钟；
- 相同资源预算；
- 明确的比较指标。

只证明 candidate 自己能运行，无法证明优化有价值。

### 5.5 必须设置负面对照

负面对照故意恢复已知坏行为，并要求断言失败，例如：

- FIFO 队列造成可见请求饥饿；
- 周期性扫描整份文档；
- 固定缓存前 64 页而不跟随阅读方向；
- 首屏前解析完整工作表；
- 移动端请求省略 document ID；
- 接受旧 epoch 的结果。

如果旧架构和新架构都能通过，门禁没有区分力，属于无效测试。

### 5.6 绑定生产代码

纯模型通过仍可能遗漏生产接线。必须至少选择一种绑定方式：

1. 直接导入并测试生产模块；
2. 让模型读取生产配置或生成物；
3. 对关键协议、常量和调用点做静态断言；
4. 编写组件集成测试，用 fake transport/clock 调生产代码；
5. 在构建后对符号、资源、Manifest、路由或包内容做检查。

KOffice 的共享热 Core 初版仿真验证了 epoch 生命周期，却没有约束 Android 首条请求必须携带
正数 `appDocId`，因此真实设备触发 `DocumentBroker` 断言。改进后的门禁同时包含：

- 模型断言连续文档 ID 为正且唯一；
- 请求字符串必须包含 `<url> <appDocId>`；
- 静态源码检查必须存在 ID 分配、正数校验和协议拼接；
- C++ 编译、链接后再上真机。

这说明仿真的重点不是增加数量，而是让断言覆盖真实的生产连接点。

## 6. 标准执行流程

### 阶段 A：立项

1. 写清用户问题和当前证据；
2. 标出哪些变量可在设备外验证，哪些只能真机验证；
3. 记录基线数据和已知失败模式；
4. 定义本轮成功门槛与停止条件。

### 阶段 B：建模

1. 定义状态、事件、资源和身份；
2. 实现 baseline；
3. 实现 candidate；
4. 加入正常、压力、边界、错误和超时输入；
5. 加入负面对照；
6. 输出结构化指标。

### 阶段 C：校准

1. 使用少量真实历史数据校准数量级，不追求拟合每一帧；
2. 检查单位、时钟、并发和内存计算；
3. 改变输入规模，确认复杂度趋势符合设计；
4. 重复运行，确认结果确定且没有偶然通过。

### 阶段 D：生产化

1. 实现生产代码；
2. 增加模型—生产绑定检查；
3. 运行格式、语法、静态、补丁重放或单元测试；
4. 在 CI 前置 job 运行仿真；
5. 仿真失败则停止构建。

### 阶段 E：制品与真机

1. 编译、链接、打包；
2. 校验制品尺寸、哈希、签名和压缩包完整性；
3. 在指定设备、指定屏幕、指定入口运行固定脚本；
4. 验证打开、内容、交互、错误、退出和重开；
5. 记录真实耗时、FPS、截图、日志、PID/内存；
6. 把真机差异反馈到模型，而不是只改真机参数。

### 阶段 F：结论

只能使用以下分层结论：

- `SIMULATION PASS`：设备外不变量通过；
- `BUILD PASS`：生产代码已编译、链接和打包；
- `DEVICE PASS`：指定设备与用例通过；
- `PRODUCT PASS`：完整用户闭环、回归矩阵和发布条件通过。

禁止把前一层写成后一层。

## 7. 仿真过程如何记录

每次报告至少包含：

1. 目的：要排除什么风险、支持什么决策；
2. 范围：覆盖和不覆盖的系统边界；
3. 版本：代码提交、模型版本、配置版本；
4. 环境：OS、语言版本、CPU 架构（若相关）；
5. 输入：合成数据、真实夹具摘要、随机种子；
6. 假设：资源、时钟、线程、缓存、失败概率；
7. 流程：执行命令和阶段；
8. 指标：基线、候选、阈值；
9. 正向断言：候选必须满足；
10. 负面对照：旧架构必须被抓住；
11. 确定性：重复次数和机器可读输出哈希；
12. 结果：逐项 PASS/FAIL 与实际值；
13. 边界：仍需编译或真机验证的内容；
14. 下一步：构建、设备矩阵、回退条件。

推荐机器可读结果：

```json
{
  "schema_version": 1,
  "suite": "subsystem simulation",
  "status": "PASS",
  "summary": {"assertions": 16, "passed": 16, "failed": 0},
  "environment": {"runtime": "Python 3.x"},
  "inputs": {"seed": 20260805, "fixture_version": "v1"},
  "models": {},
  "assertions": [
    {"name": "stale-response-is-rejected", "passed": true, "detail": "0 accepted"}
  ]
}
```

## 8. 验收标准

### 8.1 通用硬门槛

一轮仿真只有同时满足以下条件才通过：

- 所有正向断言通过；
- 所有负面对照被检测为失败；
- 重复运行结果一致，或随机测试使用固定种子并保存种子；
- 输出包含实际值，不只有 PASS 文本；
- 输入规模覆盖正常、峰值和边界；
- 模型至少绑定一个生产连接点；
- 模型自身无未捕获异常、超时或资源泄漏；
- 文档明确声明不能由仿真证明的内容；
- CI 中仿真失败会阻止昂贵构建；
- 真机计划有固定设备、夹具、流程和回退条件。

### 8.2 性能项目附加门槛

- 同资源预算比较 baseline 与 candidate；
- 报告 P50/P95/P99 或适合该问题的分位数；
- 报告峰值而不只平均值；
- 扩大输入后验证复杂度趋势；
- 不用模型时间冒充设备毫秒；
- 真机验收使用真实 frame/gfx/perf/trace 数据重新校准。

### 8.3 容错项目附加门槛

- 正常、截断、损坏、受保护、超限和未知输入均有结果；
- 错误分类稳定、可解释；
- 不崩溃、不死循环、不无限重试；
- 修复或降级有大小、时间、深度和次数上限；
- 无法安全修复时保留原始数据并明确失败。

## 9. 常见错误

- 只测候选，不测旧架构；
- 用平均值掩盖长尾；
- 把真实生产 bug 同样复制进模型；
- 模型与生产代码没有任何绑定；
- 为得到 PASS 临时放宽阈值；
- 只测正常输入；
- 使用真实睡眠和墙上时钟，导致结果不确定且慢；
- 在 CI 中运行几十分钟，失去前置门禁价值；
- 仿真通过后跳过编译或真机；
- 用“理论 30fps”替代真实帧统计；
- 仿真失败后继续昂贵构建；
- 不保存输入、版本、JSON 和日志，导致无法复现。

## 10. KOffice 示例结果

KOffice 当前设备无关 Office 管线仿真覆盖：

- 可见工作抢占后台任务；
- 旧视口排队工作取消；
- PPT tile-ready 事件驱动合成与稳定页面几何；
- Word 阅读方向缓存、临时条带释放和页面面去重；
- Excel 首视口渐进解析、常用样式快速路径、稀疏行与错误分类；
- 热引擎正常关闭、超时回退、epoch 拒绝旧消息；
- 共享 runtime 使用正数且唯一的移动文档 ID。

当前本地结果为 17/17 断言通过；最近新增的 PPT 快速滚动模型要求最终可见页进入预览队列首位、
停止后同步为 Core 当前 part，并在 2 秒前得到非空预览。负面对照可以识别 FIFO 饥饿、PPT
全文轮询、原生滚动层与 Core viewport 脱节、Writer 固定页缓存、XLSX 全表首屏和移动文档 ID
缺失等旧行为。GitHub 对 17 项版本仍待新提交验证。该结果只表示算法与生命周期门禁通过；
真实 Word/PPT/Excel 的解码、画面、帧率和退出仍由指定副屏真机流程验收。

## 11. 可复用验收清单

在其他项目开始仿真前，逐项确认：

- [ ] 用户结果和失败现象已写清；
- [ ] 已区分可仿真与必须真机的部分；
- [ ] baseline 和 candidate 使用相同输入/预算；
- [ ] 状态、事件、资源、身份已最小化；
- [ ] 不变量已变成布尔断言；
- [ ] 有至少一个负面对照；
- [ ] 有正常、边界、压力、错误、超时输入；
- [ ] 固定种子/虚拟时钟保证可重复；
- [ ] 输出 JSON、实际指标和环境版本；
- [ ] 至少绑定一个生产连接点；
- [ ] CI 仿真位于昂贵构建之前；
- [ ] 制品有哈希、签名和完整性门禁；
- [ ] 真机设备、入口、夹具、动作和阈值固定；
- [ ] 报告明确区分 SIMULATION/BUILD/DEVICE/PRODUCT PASS；
- [ ] 真机发现的新失败已回灌为模型或静态回归门禁。

遵循这套流程，仿真的价值不是减少真机测试，而是让每一次真机测试都验证一个已经经过逻辑
筛选、可复现、可回退的候选，从而减少盲目试参和无效构建。
