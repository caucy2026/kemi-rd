# Android 双屏/单屏启动、渲染与退出架构

> 适用场景：Android 12 多显示器设备；两块物理屏均为 1920 × 1280，要求把网页作为一张连续的 1920 × 2560 画布展示。本文以 KEMI 双屏浏览器为验证对象，提炼为其他双屏应用可复用的启动、渲染和生命周期规范。

## 1. 先定义产品语义

| 模式 | 启动入口 | 显示结果 | 会话原则 |
|---|---|---|---|
| 双屏模式（默认） | 正常点击桌面图标 | D2 显示逻辑画布上半区，D0 显示下半区；上下相接，构成一张 1920 × 2560 页面 | 一个渲染会话、一个内容状态、两块输出 Surface |
| 单屏模式 | 长按图标后的“单屏模式”快捷项 | 在用户点按的物理屏显示完整 1920 × 1280 浏览器 | 只创建一个 Activity；不创建另一屏的配对窗口 |

这里的“双屏”不是镜像，也不是两个独立浏览器页面。地址、历史、Cookie、缩放、播放状态、DOM、滚动位置和下载状态都必须只有一份。两块屏只是同一帧的相邻裁切输出。

## 2. 显示角色与固定方向

本机硬件的角色固定如下：

| Display | 角色 | 页面逻辑区域 |
|---|---|---|
| D2 | 上屏 / 第一页 | 从逻辑页顶部开始 |
| D0 | 下屏 / 第二页 | 紧接 D2 的下半区 |

双屏模式锁定横屏，禁止由任一 Activity 单独旋转。不能只按“主屏/副屏”名称判断，启动和验收必须通过 `dumpsys window` 或 `DisplayManager` 读取实际 display id。

## 3. 一个渲染源，两个连续输出

推荐把浏览器内核或业务渲染层只初始化一次，并让它输出一个共享帧：

    Gecko / Web 内容会话
              │
       1920 × 2560 逻辑帧
              │
       共享 EGL / SurfaceTexture
          ┌───┴───┐
          │       │
    D2 上半裁切  D0 下半裁切

实现要点：

- 共享同一个 Gecko Session（或同一业务渲染状态），不可为 D0、D2 各建一个 WebView/Session。
- 在同一个 EGL 上下文和渲染线程中，把同一纹理分别绘制到两个 `Surface`；D2 绘制顶部，D0 绘制紧随其后的区域。
- 裁切边界不能机械写成 1280。若 D2 有地址栏、工具栏等顶端 chrome，D2 的网页可视高度为 `1280 - topChromeHeightPx`，D0 的源区域必须从该可视高度之后开始；触控坐标也应使用同一边界。
- D0 不应再绘制工具栏，否则接缝会重复；工具栏、地址栏和加载进度仅在 D2 顶部显示。
- 所有页面级动作（地址跳转、前进、后退、刷新、主页、收藏、下载）只向共享会话发送一次。

这条规则直接避免“两个屏都显示第一页”“滑动一屏另一屏抖动”“历史记录分叉”等问题。

## 4. 输入坐标与滚动联动

两个物理屏都可操作，但它们产生的输入应进入同一个逻辑页面坐标系：

    logicalY = localY + logicalOffsetOfDisplay

其中 D2 的网页内容从其工具栏下方开始，D0 的 `logicalOffsetOfDisplay` 是 D2 实际网页可视高度。不要以 Activity 高度或硬编码常量替代实际 chrome 高度。

为防止反馈环抖动：

1. 当前触摸屏是唯一输入源；
2. 同一个手势只提交给共享会话一次；
3. 另一块屏只消费该会话产生的渲染帧，不再把“同步后的滚动”回写为新的输入；
4. 地址和加载进度由共享会话单向广播。

需要输入文字时，`InputConnection`/IME 必须绑定到实际被触摸的那一个 Activity 和它当前的 Surface；否则副屏点击输入框常见“软键盘不弹”或光标不生效。鼠标右键应保留为标准上下文菜单，复制始终由选区决定，粘贴则按系统剪贴板是否为空决定可用状态。

## 5. 从任意物理屏启动双屏

最容易被忽略的失败路径是：用户在 D2 上点桌面图标，却直接把“D0 总控 Activity”启动到 D2。随后再移动或启动配对窗口，会发生任务栈与显示归属冲突，表现为闪退、两个窗口消失或黑屏。

推荐使用独立的 `DualScreenLaunchActivity` 作为桌面入口，而不是把 launcher alias 直接指向总控：

    读取 launcher Activity 所在 display
    ├─ 来源是 D0：在 D0 启动 DualScreenBrowserActivity
    └─ 来源是 D2：先 finishAndRemoveTask 当前 D2 临时任务
                 等待短暂的任务清理窗口（约 400 ms）
                 用 ActivityOptions.setLaunchDisplayId(0) 启动 D0 总控
                 由 D0 总控创建 D2 的 DualScreenTopActivity

`onUserLeaveHint()` 不能把这一内部显示迁移误判为用户离开；应在内部启动期间抑制退出逻辑。优先使用公开 API `ActivityOptions.setLaunchDisplayId()`。`chip.md` 中的反射重定向适合特定 ROM 的兼容手段，不能与本架构的任务路由混用，更不能作为默认路径。

## 6. 单屏模式：独立、干净、保留点按来源

单屏模式要做到与双屏主页和功能一致，只是渲染目标不同：

- 快捷项启动 `SingleScreenBrowserActivity`，目标 display 就是用户长按并选择菜单的物理屏；
- 只启动一个 1920 × 1280 输出窗口，不创建 D2/D0 配对 Activity；
- 单屏与双屏切换时释放旧模式的共享渲染资源，再创建新模式资源，禁止复用已经失效的 Surface；
- 单屏退出仅关闭自身；双屏退出必须关闭整个配对会话。

## 7. 双屏退出必须是一个事务

双屏会话必须有统一的 `exitAll()`：

1. 设置“正在收尾”标志，避免两个 Activity 的 `onDestroy()` 相互递归；
2. 先关闭/解绑共享 Gecko Session、EGL 和 Surface；
3. 同时 `finish()` D0 总控和 D2 顶部 Activity；
4. 清理对端 Activity、共享 session 的弱引用和启动抑制标志。

以下任一路径都应调用同一事务：D0 系统返回、D2 系统返回、任一屏工具栏退出、D0 的 HOME/真正离开、异常销毁。不要把鼠标右键或坐标溢出误识别为返回事件。

不建议为普通退出使用 `Process.killProcess()`：它会掩盖生命周期问题、影响下载/恢复并让外部调用者难以复用。仅在设备 ROM 已知存在无法回收的残留进程时，才把它作为受控的最后兜底方案。

## 8. Surface 生命周期：黑屏的核心防线

`singleInstance` 的 D2 Activity 在 HOME 后重启时可能被系统复用，Activity 仍在而底层 `Surface` 已失效。必须在 `surfaceCreated`、`surfaceChanged`、`surfaceDestroyed` 和 Activity resume/pause 中重新绑定实际 Surface：

- 每次 surface 创建后都向共享合成器注册当前有效的 TOP/BOTTOM Surface；
- 解绑旧 Surface，禁止继续向已销毁的 EGL surface 提交；
- 缓存最近一帧，在新 Surface 绑定后先绘制缓存帧，再等待内核下一帧；
- 日志记录 TOP/BOTTOM Bound 和首个 1920 × 2560 帧，冷启动与 HOME 后重启均要检查。

这样可避免“首次正常，第二次启动 D2 黑屏”的假通过。

## 9. 真机闭环验收清单

每次修改启动、Surface、输入或退出相关代码，至少执行以下最小回归：

| 项目 | 通过标准 |
|---|---|
| D0 普通启动 | D0 总控 + D2 顶部窗口同时出现，内容连续且不镜像 |
| D2 普通启动 | 经启动路由后得到同样的 D0/D2 布局，无闪退 |
| 单屏快捷项 | 仅当前屏创建单屏 Activity，无配对窗口 |
| 冷启动 + HOME 后重启 | 至少重复两轮；D2 不黑屏，日志有重新绑定和首帧 |
| D2、D0 各滚动一次 | 同一页面连续移动，无反馈抖动、无内容分叉 |
| 输入与鼠标 | 两屏输入框能弹键盘；右键菜单、复制、粘贴符合系统语义 |
| 四种退出 | D0 返回、D2 返回、D2 退出按钮、D0 HOME 均让双屏 Activity 同时消失 |
| 证据 | 保存两屏截图/录像、`dumpsys window`、合成器日志和 `FATAL EXCEPTION` 检查结果 |

## 10. 常见故障速查

| 现象 | 常见根因 | 修复方向 |
|---|---|---|
| D2 点击图标后闪退 | D0 总控被错误创建在 D2 的任务上 | 使用独立启动 Activity，清理 D2 临时任务后显式路由至 D0 |
| 两屏都是第一页 | 两个独立会话或两块 Surface 裁切同一源区 | 单会话、共享帧，按连续逻辑 y 区域裁切 |
| 一屏滚动时另一屏来回抖 | 两端把同步滚动再次发送为输入 | 触摸源独占，另一屏仅渲染 |
| D2 偶发黑屏 | retained Activity 复用了失效 Surface | 重绑 Surface、缓存首帧、重复冷启动验证 |
| 工具栏覆盖/接缝错位 | 裁切和触控使用了固定 1280 边界 | 以动态 `topChromeHeightPx` 计算网页边界 |
| 任一屏退出后另一屏残留 | 没有共享关闭事务 | 所有退出路径统一调用 `exitAll()` |

## 11. 与通用双屏文档的边界

`chip.md` 侧重芯片平台上“异显/镜像”、`Presentation` 和 ROM 兼容重定向。本文件侧重浏览器、文档阅读器、地图等需要“一份连续内容跨两屏”的应用：核心是共享状态、共享帧、相邻裁切和原子退出。选架构前先明确产品是“两个独立/镜像窗口”，还是“一个跨屏连续画布”；两者不能混用。
